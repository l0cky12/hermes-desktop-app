# Over SSH, Kanban and Skills go through the hermes CLI, not ACP

Over SSH the client already runs `ssh <host> hermes acp` for chat, but ACP carries only session and prompt methods: Hermes exposes the Board and Skills to ACP clients solely as tools the agent itself can call (`acp_adapter/tools.py`), never as RPC methods. So for Kanban and Skills the client opens a separate one-shot `ssh <host> hermes …` per action instead: `hermes kanban list|show|assignees|create|comment|dispatch --json` for the Board, `hermes config get|set skills.disabled` for toggling a Skill, and, because `hermes skills list` prints only a truncated table with no descriptions, a short read-only shell script that finds the active Profile's home with `hermes config path` and prints each SKILL.md's frontmatter under its `skills/` directory (hidden directories skipped, as Hermes does). Running Hermes's own Python skill finder was considered, but the launcher offers no supported way to run a snippet, and the script needs nothing beyond `find`, `awk`, and `cat`.

Asking the agent over ACP to do it ("list my kanban tasks") was rejected: it spends a model call per refresh, returns prose rather than data, and can't be trusted to toggle a Skill exactly. Reading `kanban.db` or `config.yaml` over SSH directly was rejected too: it bypasses Hermes's own rules (board resolution, active Profile, essential Skills that can't be disabled) and breaks when those files change shape. SKILL.md files are the exception: they are Hermes's documented skill format, and the listing still takes the Profile and the disabled list from `hermes` itself. It does not follow `skills.external_dirs`.

Consequences: each action costs an SSH connection setup (ControlMaster in the user's ssh_config makes it cheap), there are no live Board updates over SSH, and every user-supplied value (task title, comment text, skill names) reaches a remote shell, so it is single-quote escaped and task bodies travel on stdin (`--body-file -`).
