# The Remaining limit comes from Hermes's `hermes usage` document, never from the providers directly

The Usage view shows the Remaining limit of the Codex and Claude subscription accounts the active Profile uses on the Gateway host. Hermes already fetches these (`agent/account_usage.py`, calling ChatGPT's `/backend-api/wham/usage` and Anthropic's `/api/oauth/usage`) and prints them as a stable JSON document with `hermes usage --provider <p> --json`. So over SSH the client runs `hermes -p <profile> usage --provider <p> --json` one-shot, as in ADR 0002. Over the Dashboard it calls a `GET /api/analytics/account-usage?provider=&profile=` route, contributed upstream, which returns the same document. The route shells out to that same `hermes -p <profile> usage` command, because Hermes reads `HERMES_HOME` once at import time and so one Dashboard process can't resolve another Profile's credentials in-process. One parser handles both. Exit 1 (no account with that provider) is `null` on both paths, so the client can keep a 404 for "this Hermes has no such route".

Having the client read the OAuth tokens from the host and call the providers itself was rejected: it copies subscription credentials off the Gateway host and bypasses Hermes's credential resolution per Profile. The `/api/ws` `session.usage` sidecar was rejected too: it needs a live TUI session, covers only the configured provider, and returns pre-rendered text rather than data.

Consequences: a Gateway whose Hermes predates the route shows "needs a newer Hermes" instead of the Remaining limit over the Dashboard. Only Codex and Claude are asked for, so a Profile on another provider shows none. The view is read-only; redeeming a banked Codex reset is deliberately not offered.
